# 审计：每周 10 分钟

审计回答两个问题：

1. **记录是否完整**：条目字段齐不齐、决策记录有没有理由、技能有没有 description；
2. **机制是否有效**：捕获量、晋升率、过期 raw、重复条目是否在合理区间。

格式全绿不等于有效——用户仍在重复纠偏，就是机制没生效。

## 一、每周流程

```bash
# 1. 完整性检查（退出码 1 = 有错误）
python3 <skill>/scripts/distill.py audit

# 2. 周报（直接发给用户）
python3 <skill>/scripts/distill.py digest --days 7
```

顺序固定：先修 `audit` 报的错，再看 `digest` 的数据。

## 二、读 audit 输出

| 输出 | 含义 | 动作 |
| --- | --- | --- |
| `✗ 缺字段` | 条目或决策记录不完整 | 补字段；补不出的写「未说明」，不要编 |
| `✗ 状态非法` | 状态不在 `raw/confirmed/promoted/dropped` | 按实际状态改 |
| `✗ frontmatter 缺 name/description` | 技能无法被触发 | 补 frontmatter |
| `⚠ raw 已超过 N 天` | Triage 没跑 | 本周内处理，或标 `dropped` |
| `⚠ 原话未逐字引用` | 可能是转述 | 改回原话；确实没有就标 `agent 推断` |
| `⚠ 重复原话` | 同一洞察记了多次 | 合并为一条，保留重复次数作为晋升信号 |
| `⚠ 索引未登记` | 写了但找不到 | 补索引 |

`audit` 退出码：

- `0`：PASS，可有警告；
- `1`：FAIL，必须先修错误再交付。

## 三、读 digest 数据

| 指标 | 健康区间 | 偏离时的动作 |
| --- | --- | --- |
| 每周捕获 | 3–10 条 | 0 条：检查交付前是否执行三问；>10 条：收紧捕获触发点 |
| 晋升率 | 20–40% | 100%：捕获太窄；<15% 且基数大：多为噪音 |
| 过期 raw | 0 | 每次交付前限时 3 分钟处理 |
| 重复原话 | 0 | 记录前先搜 inbox |
| 用户纠偏 | 下降 | 同类纠偏重复 = 规则太模糊或没落地 |

比率要看基数：只有 2 条记录时，100% 晋升不说明问题；连续两周且基数 ≥ 5 才据此调整。

## 四、周报模板

把 `digest` 的输出整理成下面四段发给用户，不要只附原始输出：

```markdown
## 本周蒸馏
- 新增 N 条（类型分布）
- 晋升 N 条：<去向>
- 新增决策记录 N 条
- 待处理：raw N 条（过期 N 条）

## 待你确认
- <拟升级为用户规则的条目：原文 + 适用范围>

## 建议
- <基于数据的 1–2 条调整，不写套话>

## 下周重点
- <最多两条>
```

「待你确认」只放**用户原话拟升级为规则**的条目；agent 推断按证据自行晋升，但在「本周蒸馏」里说明。

## 五、失效修正

| 现象 | 先改什么 |
| --- | --- |
| 一周 0 条 | 把 Capture 三问写进交付清单；触发点改得更具体（带例子） |
| 大量 raw 过期 | Triage 从「有空再做」改为「交付前 3 分钟」 |
| 晋升后同类问题仍出现 | 检查规则是否可判定；补验证方式与例外 |
| 审计总 PASS 但用户仍纠偏 | 把最近三次纠偏逐条对照 inbox，补漏掉的触发点 |
| 条目越记越水 | 收紧「什么值得记」，把一次性问题标 `dropped` |

每次调整只改一条规则，下周看数据；不要一次改完所有阈值，否则无法判断哪条生效。

## 六、常见误判

- **把「写了规则」当成「生效了」**：生效的判据是下一次同类任务的动作变了，不是文件里多了一行。
- **把「条目多」当成「蒸馏好」**：只捕获不晋升，等于把 inbox 变成垃圾桶。
- **把「晋升率高」当成「质量高」**：没有过滤的晋升会让规则文件膨胀，执行时被忽略。
- **只审计 agent 的记录**：用户的纠偏、确认、否决同样是素材，漏掉它们就只剩 agent 自说自话。

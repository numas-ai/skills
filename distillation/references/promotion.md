# 晋升：从记录到执行单元

晋升不是「整理笔记」，是**改变下一次的行为**。
一条记录晋升后，如果没有任何文件、流程或检查项发生变化，这次晋升就是无效的。

## 一、晋升门槛

同时满足才晋升：

1. **可复用**：预期还会再遇到，不是一次性问题；
2. **可验证**：有明确的成功判定（命令、检查项、可观察的行为差异）；
3. **有证据**：来自实测、返工或用户明确表达，不是推测；
4. **归属正确**：知道该落在哪个仓、哪个文件、哪个范围；
5. **不重复**：先查现有规则 / 技能 / 工具，能补充就不新建；
6. **改变未来行为**：写清「下次遇到同类问题，动作会有什么不同」。

任一条不满足：留在 inbox，标 `confirmed` 或 `dropped`，写清原因。

## 二、去向判定

| 记录类型 | 去向 | 判定问句 |
| --- | --- | --- |
| 决策 / 约束 | 规则文件（`AGENTS.md` 等）或 `decisions/` | 有取舍、会约束后续实现吗？ |
| 方法 / 坑 | 技能 `SKILL.md` | 同类问题会反复出现，且有稳定做法吗？ |
| 可脚本化检查 | 工具脚本 | 手工做容易错，或每次都重复吗？ |
| 独立上下文角色 | 角色卡 | 任务能整块交出去，且不需要中途确认吗？ |
| 一次性 | 留在 inbox | 不预期复现吗？ |

判定顺序：**能写成脚本的优先做工具**；需要判断但不必独立上下文的写技能；要独立上下文长时间干活的才做角色卡。

## 三、规则

规则是约束，不是口号。写进规则前：

1. 把**用户原话**和**适用范围**给用户确认；
2. 改写成可判定条款：出现什么条件、必须/禁止做什么；
3. 写清例外，否则执行时会出现「这次算不算」的争议；
4. 在条目里填 `晋升到: <文件>「<小节>」`。

差的规则：

```markdown
- 注意文档质量。
```

好的规则：

```markdown
- 交付前必须跑 `scripts/check.sh`，退出码非 0 不得交付；
  图片另跑 `check.py`，允许的例外只有「纯装饰图」，需在交付说明里写明。
```

规则落点：

- 跨项目约束 → 工作区 / 组织级规则文件；
- 单项目约束 → 该项目根目录的规则文件；
- 只约束某个角色 → 该角色卡，不写进全局规则。

## 四、决策记录

有取舍、且以后可能被问「为什么不是另一个」时，写决策记录，不硬塞进技能。

文件：`decisions/NNN-<kebab-case>.md`，编号连续。

必备内容：

| 部分 | 写什么 |
| --- | --- |
| 背景 | 为什么现在要决定，约束是什么 |
| 选项 | 至少两个可行选项，各自好处与代价 |
| 决定 | 选了什么，一句话 |
| 理由 | 事实与判据，不写「感觉更好」 |
| 影响 | 约束哪些后续实现、接口、目录或流程 |
| 复盘点 | 什么条件下需要重新看这个决定 |

被新决策取代时：新记录写 `Supersedes: NNN`，旧记录改 `状态: superseded` 并链接新记录。

## 五、技能

先改现有的，不要新建：

1. 查技能索引，有没有已经覆盖同类问题的 `SKILL.md`；
2. 有 → 补步骤、补判据、补坑，并在「失效时改什么」里加一行；
3. 没有 → 新建 `SKILL.md`，frontmatter 至少写 `name` 与 `description`，description 必须写清「什么时候用」；
4. 技能要交出**推理过程 + 自检闭环 + 修正路径**，不是「照抄即用」的文案；
5. 有可执行校验的，把脚本放 `scripts/`，给出 PASS/FAIL 与退出码。

晋升后更新技能索引，避免「写了但找不到」。

## 六、工具

工具的门槛是**可重复执行、结果可判定**：

- 一条命令能跑完，不依赖手工步骤；
- 有明确退出码：0 = PASS，非 0 = FAIL；
- 失败时输出能定位问题的信息，不只说「失败」；
- 不写死本机路径；路径从参数、配置或脚本位置推导；
- 临时产物写到临时目录，用完清理。

工具写完后，至少用一个正例和一个反例实测，把命令与输出记进证据。

## 七、丢弃

以下情况标 `dropped`，并在条目里写一句原因：

- 一次性问题，不预期复现；
- 证据不足，无法验证；
- 与现有规则 / 技能重复，且没有新增信息；
- 环境已变化，做法不再适用。

丢弃不是失败——**长期 100% 晋升才说明没有过滤**。

## 八、晋升后的动作

1. 修改目标文件（规则 / 技能 / 工具 / 决策）；
2. inbox 条目改 `状态: promoted`，补 `晋升到`；
3. 更新对应索引（规则目录、技能表、工具表）；
4. 在项目日志追加一行：改了什么、落在哪、怎么验证；
5. 如果晋升改变了交付流程，把检查项加进交付清单。

## 九、回滚

晋升错了要能撤：

- 规则：删掉条款，或在下一行写更正，不保留「历史版本」占位；
- 技能：回退对应小节，保留触发这次修订的事实；
- 工具：删除脚本并从索引移除；
- 决策：写新记录 `Supersedes` 旧记录，不直接改历史理由。

回滚同样记日志，并说明触发回滚的证据。

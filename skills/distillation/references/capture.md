# 捕获：记什么、怎么记

捕获层的唯一目标是**留下可回看的原始素材**，不在这里做最终归类。
判断标准只有一条：三个月后，另一个 agent 看到这条记录，能不能还原「当时为什么这么说」。

## 一、什么值得记

命中任意一条就记：

| 信号 | 例子 |
| --- | --- |
| 用户给出原则 / 约束 | 「生产不许开特权」「回答先给结论」 |
| 用户纠正了你的做法 | 「不是这个意思，我是说……」 |
| 用户在选项里做了取舍 | 选了 A 不选 B，并给了理由 |
| 用户确认了一个非显然的做法 | 「对，就这样」+ 该做法以后还会用 |
| 返工 / 事故 / 误判 | 同一个坑第二次踩，或一次交付被退回 |
| 重复劳动 | 同一个手工步骤做了两次以上 |
| 从结果反推 | 产物为什么做成这样，换个场景该怎么决策 |

不记：一次性的排错细节、没有复用价值的闲聊结论、能从代码直接看出来的事实。

## 二、四条记录规则

### 1. 原话逐字引用

```markdown
- 原话: "以后汇报先给结论，再给细节"
```

- 引号内必须是用户说过的原句，不改写、不润色、不合并；
- 用户没说理由时写 `理由未说明`，**不要替用户编**；
- 只有 agent 的总结时写 `agent 推断：...`，不得伪装成原话；
- 一句话里既有原话又有推断时，分开写：

```markdown
- 原话: "这个交互太绕了"
- 推断: agent 推断：用户希望减少确认步骤（证据不足，待确认）
```

### 2. 场景写触发条件

场景不是「当时在做什么」的流水账，而是**以后什么情况下这条适用**。

- 差：`场景: 讨论方案时`
- 好：`场景: 给用户汇报多方案对比，先讲了背景和推导，用户打断要求先给结论`

### 3. 证据可复核

可接受的证据：会话日期与轮次、提交号、日志行、命令与原始输出、返工记录链接。
不可接受：`感觉`、`应该是`、`一般来说`。

### 4. 候选只写一个主去向

`规则 | 技能 | 工具 | 角色 | 决策 | 仅日志`
拿不准时写 `仅日志` 并标 `状态: raw`，留给 Triage 决定；不要一条记录挂三个去向。

## 三、条目模板

```markdown
### E-YYYYMMDD-NN · <类型>
- 原话: "……"
- 场景: ……
- 证据: ……
- 候选: 规则 | 技能 | 工具 | 角色 | 决策 | 仅日志
- 状态: raw
```

类型取值：

| 类型 | 含义 |
| --- | --- |
| `decision` | 有取舍的选择 |
| `preference` | 用户的偏好、口味、表达习惯 |
| `method` | 可复用的做法、步骤、判断标准 |
| `pitfall` | 踩过的坑、返工原因、误判 |
| `tool` | 可脚本化的重复劳动 |
| `agent` | 需要独立上下文的角色 |
| `one-off` | 一次性问题 |

编号按天自增：`E-20261024-01`、`E-20261024-02`。
同一天追加条目时不要重排旧条目；状态变化只改 `状态` 字段，必要时补 `晋升到`。

## 四、好例 / 坏例

**坏例：只有结论，无法复用**

```markdown
### E-20261024-01 · pitfall
- 原话: "这里有问题"
- 场景: 调试时
- 证据: 无
- 候选: 技能
- 状态: raw
```

问题：不知道是什么问题、什么条件下会再出现、凭什么判断修好了。

**好例：可还原、可验证**

```markdown
### E-20261024-02 · pitfall
- 原话: "别用端口转发验证，入口必须走 *.localhost"
- 场景: 本地 K8s 验证服务入口时，agent 用 kubectl port-forward 绕过 ingress
- 证据: 2026-10-24 会话；用户纠偏；随后改用 LoadBalancer + host 访问通过
- 候选: 规则
- 状态: promoted
- 晋升到: AGENTS.md「本地验证」节
```

**坏例：把推断写成原话**

```markdown
- 原话: "用户希望所有文档都用中文"
```

用户没说过这句话，是 agent 从几次修改里总结的。应写成 `agent 推断：...`，并在晋升前向用户确认。

**好例：一条只讲一件事**

```markdown
### E-20261024-03 · preference
- 原话: "一次只问一个问题，别批量抛"
- 场景: 交付前同时有 3 个待定项，agent 用一次提问全抛给用户
- 证据: 2026-10-24 会话；用户明确要求
- 候选: 规则
- 状态: promoted
- 晋升到: AGENTS.md「交互」节
```

## 五、隐私与安全

inbox 会被提交、被别的 agent 读到，记录前先脱敏：

- 令牌、密钥、口令一律写 `<hidden>`；
- 内网地址、真实主机名、客户名称按需替换为占位符；
- 不把完整的生产配置、日志原文粘进来，只留定位信息。

## 六、常见问题

**Q：用户一句话里有三条原则，记几条？**
按原子性拆成多条，每条一个编号；不要写成一段散文。

**Q：用户说得含糊，要不要追问？**
先按原话记，`场景` 里写「适用范围待确认」；Triage 时再决定是否追问。不要为了记录完整而打断用户。

**Q：同一个原则用户说过两次，记两次吗？**
第二次记一条并注明「重复出现」，这是晋升信号；不要合并掉重复次数。

**Q：agent 自己发现的坑，没有用户原话，能记吗？**
能，`原话` 写 `agent 推断`，`证据` 必须是可复核的失败与修复过程。

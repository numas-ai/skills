# 想法与经验蒸馏

**蒸馏的产物不是笔记，是下一次会改变行为的执行单元。**
一条记录写完后，如果 AI 下次遇到同类问题仍按老样子做，它只是被存档，没有被蒸馏。

## 什么时候用

- 用户表达原则、约束、偏好或纠偏：「必须 / 不要 / 以后都 / 我倾向 / 不是这个意思」；
- 用户在多个选项里做了选择，且以后还会遇到同类选择；
- 发生返工、事故、误判，或同一个手工步骤重复了两次；
- 交付前自检：这次有没有值得留下的东西；
- 每周复盘：捕获量、晋升率、过期条目。

不适用：一次性的排错过程、没有复用价值的聊天结论——记日志就够。

## 四条铁律

1. **用户原话逐字引用**。改写后的句子只能叫「agent 推断」，必须标注。宁可留白，也不替用户编理由。
2. **捕获要宽，晋升要窄**。先记下来，再决定去哪；不要为了凑数把一次性问题写成技能。
3. **晋升必须改变未来行为**，并且写清归属（哪个文件 / 哪个范围）和验证方式（命令 / 检查项）。
4. **用户原话升级为规则前，必须让用户确认原文与适用范围**；agent 推断晋升时，必须有证据和验证，并在交付摘要里说明。

## 日常闭环

| 环节 | 频率 | 产出 |
| --- | --- | --- |
| Capture | 随时 | `inbox/YYYY-MM-DD.md` 里的一条原始记录 |
| Triage | 每次交付前，3 分钟 | 每条的去向：规则 / 技能 / 工具 / 决策 / 丢弃 |
| Promote | 过门槛才做 | 规则、技能、工具或决策记录 |
| Audit | 每周 10 分钟 | 数据 + 待修正项 |

### 1. Capture

触发点（任一即记，不要等任务结束）：

1. 用户表达原则 / 约束 / 偏好 / 纠偏；
2. 提问得到的答案以后还会遇到；
3. 返工、失败、事故，或同一手工步骤重复两次；
4. 交付时用户确认了一个非显然的做法；
5. 从结果反推，发现「为什么做成这样」值得留给下一次。

条目格式（一条一个洞察，不写散文）：

```markdown
### E-20261024-01 · preference
- 原话: "以后汇报先给结论，再给细节"
- 场景: 方案汇报时先铺了三段背景，被用户打断
- 证据: 2026-10-24 会话；用户纠偏
- 候选: 规则
- 状态: raw
```

写法要求：

- `原话` 必须带引号且逐字；没有原话时写 `agent 推断：...`；
- `场景` 写清触发条件，否则以后无法判断是否适用；
- `证据` 写会话 / 提交 / 日志 / 命令输出，不写「感觉」；
- `候选` 只写一个主去向；
- 状态：`raw` → `confirmed`（确认值得留）→ `promoted`（已落地）/ `dropped`（不晋升，写原因）。

详见 [`references/capture.md`](references/capture.md)。

### 2. Triage（交付前三问）

1. 本次用户明确表达过什么原则 / 偏好 / 决策？（有就逐字引用）
2. 有没有返工、重复劳动或新踩的坑？
3. 每条该去哪里？

| 类型 | 去向 | 判定 |
| --- | --- | --- |
| 决策 / 约束 | 规则文件 或 `decisions/` | 有取舍、会约束后续 |
| 方法 / 坑 | 技能（`SKILL.md`） | 会复现、有稳定做法 |
| 可脚本化检查 | 工具脚本 | 手工易错或重复 |
| 独立上下文角色 | 子智能体角色卡 | 能整块交出去 |
| 一次性 | 留在 inbox，标 `dropped` | 不预期复现 |

### 3. Promote

过「蒸馏标准」+ 两条：

- **改变未来行为**：晋升后遇到同类问题会做出不同动作；
- **有归属和验证**：写清落在哪个文件 / 哪个范围，怎么验证生效。

落地动作：

- **规则**：把用户原话与适用范围给用户确认后，写进规则文件；inbox 条目改 `promoted` 并填 `晋升到`。
- **决策**：在 `decisions/` 建 `NNN-<kebab>.md`，写背景 / 选项 / 决定 / 理由 / 影响 / 复盘点。
- **技能**：更新现有 `SKILL.md` 的步骤或坑；没有合适的才新建。
- **工具**：写成可直接跑的脚本，给出 PASS/FAIL 与退出码。
- 每晋升一次，在项目日志追加一行事实记录。

详见 [`references/promotion.md`](references/promotion.md)。

### 4. Audit（每周）

```bash
python3 <skill>/scripts/distill.py audit
python3 <skill>/scripts/distill.py digest --days 7
```

`audit` 查格式与完整性（退出码 1 = 有问题）；`digest` 出周报：新增、晋升、待确认、过期 raw、重复条目，并按数据给出修正建议。
把 digest 直接发给用户，不要只报「一切正常」。

## 失效时改什么

| 症状 | 病因 | 修正 |
| --- | --- | --- |
| 一周 0 条 | 触发点太抽象；交付前没执行 Triage | 把三问放进交付清单；先记再判断 |
| 晋升率 100% | 捕获太窄，只记「够格」的 | 放宽捕获，在晋升端过滤 |
| 过期 raw 越积越多 | Triage 没跑 | 每次交付前限时 3 分钟处理 |
| 同类纠偏反复出现 | 规则太模糊或没落地 | 把原话改写成可判定条款，补验证方式 |
| 条目只有结论没有场景 | 记录时偷懒 | 先抄原话与场景，再写结论 |
| 审计长期全绿但用户仍纠偏 | 审计只看格式 | 每周对照「用户纠偏」记录，补触发点 |

## 文件布局

```text
.distill/
  config.json          # 路径与阈值
  inbox/YYYY-MM-DD.md  # 原始捕获
  decisions/           # 有取舍的决策记录
```

初始化：

```bash
python3 <skill>/scripts/distill.py init
```

默认把 inbox 与 decisions 放 `.distill/`；规则 / 技能 / 工具目录自动探测已有位置（`AGENTS.md`、`.opencode/skills`、`skills/` 等），结果写进 `config.json`，可手改。

## 反模式

- 把 agent 的总结写成「用户原话」；
- 只记结论，不记场景和证据；
- 把一次性问题写成技能，或把同一件事在多处重复记录；
- 用户没确认就把原话升级成规则；
- 审计只看格式，不看「同类返工是否减少」。

## 度量（试跑两周）

| 指标 | 目标 | 读法 |
| --- | --- | --- |
| 每周捕获 | 3–10 条 | 0 条 = 触发点没生效；过多 = 捕获太宽 |
| 晋升率 | 20–40% | 100% = 没过滤；过低 = 噪音多 |
| 过期 raw | 0 | 超期 = Triage 没跑 |
| 同类返工 | 下降 | 同一个坑不再重复 |
| 用户纠偏 | 下降 | 「不是这个意思」变少 |

两周后按数据调整触发点与门槛，不凭感觉。

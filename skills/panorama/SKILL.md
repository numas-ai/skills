# 分层全景图（`.pano`）

用户在产品里提出「画一张全景图 / 架构图 / 结构图 / 总览图」或要求更新已有图时，**直接使用本技能产出或修改 `.pano`**：不要先问用哪个工具，也不要另存图片副本。

## 十分钟路径（默认走这条）

1. 写 `bands`：3–6 层，`label` 只写中文语义；
2. 写 `nodes`：只写 `id` / `band` / `title` / `sub`，**不要写坐标**；
3. 写 `edges`：只写 `from` / `to` / `url`（发生了什么动作）；
4. 按用户想理解的流程声明 `flows`：trigger 是交互入口，paths 写完整路径、分支和回环；
5. 跑校验 → 通过后直接在 IDE 打开 `.pano`，插件按层自动排行、按文字算宽；
6. 逐个 hover 已声明 trigger，检查高亮和流动路径与该 trigger 的 paths 一致；未声明节点 hover 无流程效果；
7. 需要微调时，用户在插件里拖节点 / 改大小 / 拖折点 / 拖标签，插件自动写回。

> 只要有一个节点写了 `x` / `y`，插件就视为手工布局，整图不再自动排版。


**设计纲领（一切判断的起点）**

1. **内容层（AI 负责）**：把意思表达清楚——每个节点是什么、属于哪一层、和谁相连、连接意味着什么动作。数据必须**自带语义**（层、标题、副标题、带语义的边标签），不靠图外文档补解释。
2. **渲染层（插件负责）**：让数据**自己说话**——悬停给出节点自解释、链路亮起并流动、闭环闭合。渲染不是"把数据画一遍"，而是把结构翻译成可理解的表达。

判定一句话：**删掉图外的解释文档，只看这张图，能不能读懂。** 读不懂，就回到对应章节修数据或修推导规则，而不是写更多说明文字。

一句话分工：**AI 维护数据，插件负责让人看懂，人负责判断对不对。**

```
人：要一张能看懂 X 的全景图 / 这里改一下
AI：改 .pano → 跑校验 → 交付
人：在插件里看效果、拖两下微调 → 继续提要求
```

## 一、产物形态

正式且唯一的形态是 **`.pano`**（YAML，JSON 也能读），由工作台插件在 IDE 里渲染与编辑；改动先写回文档，再由 OpenSumi 的自动保存机制落盘，不需要手动保存。

- 一张图只维护一份 `.pano` 数据源；不要再另存图片副本并长期并行维护。

---

## 二、什么时候该产出

命中任意一条就该画：

- 要讲**系统由哪些部分组成、彼此怎么连**（分层 + 调用关系），而不是单条请求的先后；
- 要讲**闭环**：流量走出去又回来、控制面与数据面如何配合（隧道、回连、注册激活这类）；
- 要让人**一张图看懂全貌**，并能按需深入某个节点（悬停看它是什么、为什么存在）；
- 已有 `.pano` 所描述的系统**发生了变化**（新增服务、换了入口、改了链路）。

**不该用**（选了会做无用功）：

| 需求 | 更合适的产物 |
| --- | --- |
| 一次请求/一次调用的先后顺序 | 时序图 |
| 精确数值、对比 | 表格 |
| 文件/类/模块的从属目录 | 目录树或依赖图 |
| 只有两三个节点的简单关系 | 一段文字 |

> 图不是为了好看，是为了**把链路摆出来对齐**。画完如果没有任何一条链路被质疑或修正，说明它没达到目的。

## 三、内容怎么从素材推导

> 素材不足先问：不要凭印象补节点、补链路；没有依据的关系不画。

顺序固定：**先边界 → 再分层 → 再实体 → 再链路 → 最后语义标签与布局**。
跳步最典型的后果是「节点一堆、看不出层次」，或「连线都在、说不清发生了什么」。

### 1) 先定边界

明确这张图回答什么问题、到哪一层为止（要不要画到 Pod 级别？要不要画用户侧？）。边界写进交付说明。

### 2) 分层（`bands`）

层的划分依据是**运行位置与职责**，不是团队或代码仓。常见切法：

| 层 | 判据 | 典型成员 |
| --- | --- | --- |
| 本地 / 用户侧 | 跑在用户机器上、不在平台内 | 桌面端、本地沙箱、本地代理 |
| 入口层 | 外部流量唯一的收口点 | 反代、ingress、网关入口 |
| 应用层 | 平台里做业务决策、创建资源的服务 | 控制面服务、调度服务 |
| 基础设施层 | 提供网络、调度、存储的底座 | 集群 API、覆盖网控制器、中间件 |

规则：

- 层名只写中文语义（应用层 / 接入层 / 服务层 / 基础设施层），**不写组件名**、不写英文；
- 一个节点只属于一层（`node.band` 只能一个值）；层数 3–6 个；
- 颜色用 `#rrggbb` 且互相能区分（浅底深底都要看得见）；
- **不要为「团队」「代码仓」建层**——和图要讲的运行关系无关。

### 3) 实体（`nodes`）

只画**「应用」和「服务」**：一个可被单独访问 / 调度 / 替换的单元。
`svc` / `deploy` / ConfigMap / Secret / 具体中间件实例是实现形态，不进图（基础设施层放中间件本身，不放下发它的配置对象）。

判定问句：*它会不会单独出现在某条调用链上、单独挂掉会被单独引用？* 是 → 建节点；否 → 收进 `sub` 一句话交代。

必写两段文字，渲染层的解释全靠它们（见第七节）：

- `title`：**它是谁**（服务名 / 组件名，不要写句子）；
- `sub`：**它是什么形态、靠什么工作**（技术栈、部署形态或职责关键词；示例只说明字段含义，禁止照抄具体名称）。

粒度：一张 10–20 个节点最容易读懂；超过 25 个先问「能不能拆成两张」。
节点宽度由文字决定（`max(标题宽, 副标题宽) + 44`，最小 118），手工写坐标时按此估宽。

### 4) 链路（`edges`）

一条边 = **一次真实发生的连接**，方向按**发起方 → 承接方**写。每写一条问一句：*这条流量真的会走吗、方向对吗？*

- **一条双工连接只画一条边**（隧道、长连接、双向流）。回程用动画表达，不要补一条 `B → A`；校验脚本会直接拦。
- 只有**条件分支**才 `arrow: true`；入口、承载、路由不带箭头；可选 / 非主链路用 `dashed: true`。
- 同一对节点不要出现两条平行边（除非确为两条独立通道，且双方都标 `parallel: true`）。

### 5) 语义标签（`edge.url`）

`url` 是历史字段名，**内容是连线标注，写「发生了什么动作」**：

| 差 | 好 | 为什么 |
| --- | --- | --- |
| 空 | `已存在 → 路由` | 空白标签让读者无法判断这是路由、调用还是调度 |
| `ide.example.com` | `本地访问 · localhost:24096` | 只有 host 时读者不知道这条线做什么 |
| `注册` | `注册·激活（出站）` | 补上方向与阶段，才看得出握手顺序 |

判断标准：**只看这条线两端和标签，别人能不能说出「发生了什么」**。地址仍要写就写进标签里，不要只留地址。

### 6) 改名 / 改后缀的连带动作

文件名一改，**必须全仓 grep 旧名**（README、AGENTS、docs、脚本、数据引用），否则留死链。

## 四、布局与表达规则（验收标准）

- 节点必须装下 `title` 与 `sub`：AI 不用小坐标压缩文字；省略坐标时交给插件按文字自动计算尺寸。
- 节点位置可以灵活调整；自动布局按层和拓扑关系组织，不把所有节点强行压成固定网格。
- 节点宽高必须装下 `title` / `sub`；节点间距必须给边标签和折线路径留出空间。
- 连线默认从最合适的节点边出发/接入，优先边中点；同一侧多条线按比例分散，不能聚集到一个点。
- 连线只允许水平线、垂直线或带圆角的正交折线；禁止斜线、曲线和自由弧线。
- 选路优先级固定为：不穿节点 → 尽量不交叉 → 水平/垂直 → 圆角折线 → 接入分散 → 少折点 → 短距离。
- 边标签不得压住节点、其它标签或关键折点；默认自动避让，用户明确要求时才写 `label` 固定位置。

## 五、连线规则（验收标准，必须全部满足）

画线只有两种形态：**水平/垂直直线**、**带圆角的折线**。没有任何曲线。

> 手工拖折点/标签也必须遵守这条：插件不会阻止你拖出斜线或硬折，但验收按 L1 检查。

| # | 规则 |
| --- | --- |
| L1 | 只能是直线或圆角折线；禁止贝塞尔曲线、抛物线、斜直线、直角硬折 |
| L2 | **折数最少**：0 折 → 1 折 → 2 折，能一折绝不两折 |
| L3 | 接入点必须落在节点**边上**，不允许落在内部 |
| L4 | 首段 / 末段必须**垂直于所连的边**：左右边横向进出，上下边纵向进出 |
| L5 | 不得沿节点边框平行滑行 |
| L6 | 不得穿过任何节点 |
| L7 | 不得交叉（一横一竖相交即失败） |
| L8 | 不得重叠（同向共线且重叠 > 6px 即失败） |
| L9 | 同一对节点之间的多条线必须错开，绝不共线 |
| L10 | 同一节点同一侧多条边按比例均匀等分；只有一条时落在该侧中点 |
| L11 | 优先让多条连接落在不同边上（四周均匀），再压缩折数 |
| L12 | 有横向位移时：起点走水平边、终点走垂直边 —— 天然只折一次 |

**谁来算**：`.pano` 由插件按节点几何自动布线。
所以**默认不要手写 `sSide` / `tSide`**——写死会盖掉自动优化，节点一挪就变斜线；只在自动结果确实不满意时用。
拖节点后连线会实时重算；若看见斜线，先删掉手工接入侧再检查。

## 六、结构与标注

0. 不写坐标时，插件自动完成同层对齐、行内居中、按文字算宽；以下是手写坐标时的验收规则。
1. 自动布局以层和真实链路为约束；同层节点可按连接关系灵活错位，不强制固定网格；
2. 节点尺寸必须能装下文字；节点之间留出边标签和正交折线空间；
3. 画布比内容留出边距；有冲突时优先保证语义可读和连线不交叉；
4. 标注默认避让节点与其它标注；手工位置也必须不遮挡；
5. 标注之间、标注与节点之间**不得重叠**；
6. 箭头是**开放式 V 形**（`fill: none`），不是实心三角形，且只用于条件分支。

## 七、从结构推出语义（核心方法）

> 图的价值不在"画出来"，而在于**读者能读懂**。节点作用与链路串联必须**由结构推出**：不写死文案、不等用户逐条告知，也不要把某个项目的节点名/词表搬进本技能。

### 6.1 对任意节点要能回答四问

| 问题 | 依据 |
| --- | --- |
| 属于哪一层、这层做什么 | 节点的 `band` → 层 label |
| 在链路里什么角色 | **边标签语义优先**，度数兜底（见 6.2） |
| 谁调用它 | 指向它的边：来源标题 + 边标签（标签即"怎么被调用"） |
| 它调用谁 | 从它出发的边：目标标题 + 边标签 |

### 6.2 角色判定：语义优先，结构兜底

先读边标签里的动作语义，再用入度/出度和层级关系补充，不把角色绑定到节点名称或具体产品。

1. 边标签明确表达「进入 / 接收 / 请求」时，目标是承接点；
2. 边标签明确表达「调用 / 转发 / 派发 / 创建」时，源是发起或决策点；
3. 无入边、有出边 → 入口或发起点；
4. 无出边、有入边 → 落地或消费点；
5. 入度 > 1 且出度 > 1 → 汇聚与分发；仅入度 > 1 → 汇聚点；仅出度 > 1 → 分发点；
6. 其余 → 承载或转换环节。

如果标签语义与度数推导冲突，优先保留事实标签，并在交付说明中指出冲突；不要为迎合模板强行改角色。

### 6.3 意图：讲"为什么存在"，不是罗列结构

只列"属于哪些链路 / 连了谁"是不合格的表达——那是结构复述。意图由四路信息合成：

| 来源 | 提取什么 | 例 |
| --- | --- | --- |
| 层的职责 | 这一层在整体里负责什么 | 基础设施层 → "提供网络、调度与存储等底层能力" |
| 连接方向语义 | 出去建连接 / 承接进来 / 落地执行 | 有 `bind` + `注册` → "以出站方式接入，不暴露本机入站，可被按需回连" |
| 形态关键词（`sub`） | 它靠什么工作 | 从当前素材提取技术栈、部署形态或职责，不从示例复制 |
| 在链路中的位置 | 它在这条链路里做什么 | 起点 / 承载环节 / 被回连的目标 / 落点 |

**两个易错点**（都实际踩过）：

1. 层职责匹配要**先匹配更具体的关键词**（"基础设施层服务"含"服务"，先判"应用/服务"就会判错层）；
2. 闭环会让同一节点在同一条链路里出现两次，位置描述要**归并**（如"运行起点，隧道回环最终归位于此"），不要输出两条。

### 6.4 双工与闭环

- **一条双工连接只画一条边**；不要为"回程"再画一条；
- 闭环靠**动画沿环路连续跑**表达，最后一段**反向走同一条边**回到起点；
- 首尾端口不同侧时，**补一段连接**再动画，否则接缝会跳；
- 非闭环链路用**往返**推进（三角波），不要取模（取模会从终点跳回起点）。

### 6.5 链路串联（推导步骤）

1. **找入口**：该链路的入口节点（通常无入边）；
2. **走主干**：从入口沿真实边推进，不回头、不跳跃，直到该链路的落点；
3. **接双工**：隧道类边视为可双向走的**同一段**，需要回到起点时反向走它；
4. **成环**：把顺序写成数组，首尾同 id 表示闭环；
5. **并集**：某节点的悬停范围 = 它参与的**所有**链路节点并集；只取相邻节点必然碎链。

### 6.6 呈现要求（渲染层应达到的效果）

| 项 | 判据 |
| --- | --- |
| 悬停解释 | 必须给出：层 / 角色 / **意图（为什么存在）** / 上下游 / 在链路中的位置；只有标题副标题＝退化；只罗列结构不讲意图＝不合格 |
| 流动动画 | 点必须可见、连续移动；速度随链路长度自适应（短链放慢，避免频闪） |
| 无跳变 | 相邻采样位移与中位数同量级；接缝处不得突跳 |
| 高亮 | 链路节点全亮、其余压暗；控制面与数据面可区分（如虚线）；只沿链路前后追溯，不横向扩散到整个连通图 |
| 容器自适应 | 窗口 / 分栏变化后整图重新适配；**不得缩到不可读**（设最小可读缩放，低于它就居中 + 允许平移）；用户手动缩放后停止自动适配 |
| 卡片（popover） | 用卡片表达节点自己；背景半透明 + 毛玻璃，避免完全遮挡；配色跟随页面主题 |
| 无底部状态栏 | 说明只放在卡片里，避免两处重复且占高度 |
| 全屏 | 提供专注态：隐藏图例与工具条、只留画布；`Esc` 可退；宿主可能拦截浏览器全屏，失败也要能用 |
| 主题探测 | 优先用宿主注入的 `vscode-light`/`vscode-dark` 与 `--vscode-*` 变量；没有注入时再回退到实际背景亮度 / 系统偏好 |

> 像素半径、速度常数、采样窗口属于**实现参数**，写在各项目自己的实现配置里，不固化进本技能。

## 八、数据必须能「自己解释」

插件不讲稿子，它**从结构推导**每个节点的说明并做成悬停卡片。字段不是装饰，缺一项就少一段解释：

| 卡片内容 | 从哪来 | 缺了会怎样 |
| --- | --- | --- |
| 名字 / 副标题 | `title` / `sub` | 认不出它是谁 |
| 所属层 + 颜色 | `node.band` → `band.label` | 结构校验直接报错 |
| 角色 | **连线方向与数量** | 边不够，角色就说不准 |
| 意图 | **`band.label` 与 `sub` 的关键词** | 只剩泛泛的"承担该层职责" |
| 上下游、怎么连 | 边的两端 + `edge.url` | 只能报名字，说不出调用方式 |
| 在链路中的位置 | 入口节点出发的链路 | 没有明确入口节点时这一栏不出现 |

渲染层只按当前图中的自然语言标签归类，不使用固定节点名单。可识别的语义类别包括：

| 语义类别 | 常见表达 | 用途 |
| --- | --- | --- |
| 访问 / 请求 | 访问、请求、提交、读取 | 判断调用方向 |
| 转发 / 路由 | 转发、路由、分发、代理 | 判断承接与分支 |
| 创建 / 调度 | 创建、调度、分配、回收 | 判断控制点与生命周期 |
| 连接 / 握手 | 连接、注册、确认、授权、长连接 | 判断连接建立与持续承载 |
| 处理 / 转换 | 解析、转换、聚合、计算、持久化 | 判断中间处理职责 |

这些词是语义类别，不是固定词表；遇到新领域时从用户素材提取同义表达。

> 所有推导只依赖当前 `.pano` 的结构与字段（层、节点、边、标签），**不依赖任何按节点 id 写死的数据**；换一个项目同样成立。

## 九、文件格式

### `.pano`（正式形态）

```yaml
title: ''
subtitle: ''
canvas: { w: <画布宽>, h: <画布高> }
nodeHeight: <节点默认高>
bands:
  - { id: <层id>, label: <层语义>, color: '<#rrggbb>' }
nodes:
  - { id: <节点id>, band: <层id>, title: <实体名>, sub: <它是什么 / 做什么> }
    # x / y / w / h 可选；不写由插件自动分层布局
edges:
  - from: <源节点id>
    to: <目标节点id>
    url: <发生了什么动作>
flows:
  - trigger: <用户交互入口节点id>
    paths:
      - nodes: [<入口节点id>, <后续节点id>, <目标节点id>]
```

| 层级 | 字段 | 必要性 | 说明 |
| --- | --- | --- | --- |
| 根 | `canvas.w` / `canvas.h` | 可选 | 画布逻辑尺寸；不写由自动布局计算 |
| 根 | `nodeHeight` | 可选 | 新节点默认高，缺省 72 |
| 根 | `title` / `subtitle` | 可选 | 目前只存不显示，可留空 |
| band | `id` / `label` / `color` | 必填 | 颜色必须 `#rrggbb`；`label` 只写中文语义 |
| node | `id` / `band` / `title` | 必填 | `band` 必须是已定义的层 |
| node | `x` / `y` / `w` / `h` | 可选 | 不写由插件自动分层布局；写了就整图按手工坐标渲染 |
| node | `sub` | 强烈建议 | 缺了校验只给警告，但解释会退化成「只有名字」 |
| edge | `from` / `to` | 必填 | 两端必须是节点 id |
| edge | `url` | 强烈建议 | 缺了校验只给警告，但这条线的语义就丢了 |
| edge | `sSide` / `tSide` | 可选 | `top` `right` `bottom` `left`；不写由渲染器自动选最近边 |
| edge | `sRatio` / `tRatio` | 可选 | 接入点在边上的位置，0–1 |
| edge | `points` | 可选 | 手工折点 `[{x, y}]`；不写由渲染器自动正交布线 |
| edge | `label` | 可选 | 标签位置 `{x, y}`；不写放在最长段中点 |
| edge | `arrow` / `dashed` | 可选 | 布尔；箭头只给条件分支 |
| edge | `parallel` | 可选 | 布尔，**校验用标记**：同一对节点确需两条独立通道时成对标注，渲染层不读 |
| flow | `trigger` | 必填 | 用户悬停时启动流程联动的节点；未声明为 trigger 的节点 hover 无流程效果 |
| flow | `paths` | 必填 | 一条或多条节点路径；每对相邻节点必须有实际 edge；分支分别列路径，闭环首尾重复同一节点 |

`flows` 是交互语义数据，不是插件代码配置：AI 根据用户要理解的流程入口与分支声明它。插件不得内置任何具体项目的 trigger id / 路径，hover 交互只以当前 `.pano` 的 `flows` 为准。

## 十、工作流

### A. 正式形态（`.pano`，首选）

1. **读素材**：把要表达的系统组件、调用、部署位置读全（代码、文档、部署清单）。
2. **定边界与层**：写出这张图回答的问题 + 3–6 个层。
3. **列实体**：按第三节粒度筛一遍，给每个节点写 `title` + `sub`。
4. **列链路**：写成「A --动作--> B」清单，双工合并成一条，确认发起方。
5. **写意图**：每个节点的 `sub` 说明形态/职责；每条边的 `url` 说明动作和条件，不写空标签。
6. **声明交互流程**：按用户希望查看的流程入口写 `flows`，每个 trigger 声明完整 paths、分支和回环；其它节点不设 trigger。
7. **坐标**：默认省略，交给插件按节点尺寸与拓扑布局；只有精确摆放确有必要时才写坐标。
8. **跑校验**：依次运行 `check.mjs`、`quality.mjs`；失败先修数据，不用静态图片掩盖问题。
9. **IDE 验收**：用 `openfile` 打开 `.pano`，逐个验证 flows trigger 的高亮节点/边与 paths 一致，并检查节点文字、交叉、标签遮挡和流动。
10. **迭代**：发现问题时定位到「事实 / 语义 / 布局 / 渲染」四层之一，只修改对应层，重新校验。
11. **交付**：文件路径 + 图回答的问题 + 已知取舍 + 两个校验结果 + hover 流程验收结果。

结构校验之后还要跑几何质量门：

```bash
node <技能目录>/scripts/quality.mjs <文件.pano>
```

它会检查显式坐标下的节点间距、节点重叠、手工折线是否正交、折线是否穿节点和显式折线交叉；
省略坐标的文件会把布局交给插件，并由 IDE 打开后的实际画面完成最终检查。

### B. 更新已有 `.pano`

风险不在"画得对不对"，而在**把别人的手工微调弄丢**：

1. **先读全文**，不要凭记忆重建；
2. **只改该改的**：新增 / 删除节点或边时，不动无关节点的 `x/y/w/h`；
3. **`id` 保持稳定**：改 id 必须同步所有 `from`/`to` 和 `flows.trigger` / `flows.paths`；
4. **删节点时一并删边**，不留悬空引用；
5. **新增层时补齐所有节点的 `band`**；
6. 改完立刻跑校验；AI 改文件时别让人同时在界面里拖同一份文件。

## 十一、交付前质量门

按顺序过，前三项可复现，最后一项必须人看。

### 1) 结构校验（`.pano`）

```bash
node <技能目录>/scripts/check.mjs <文件.pano>   # 技能目录即本 SKILL.md 所在目录
```

`PASS` = 能被插件正常渲染且具备最小语义；`FAIL` 退出码非 0。判定分两档：

**错误（FAIL，必须修）**：字段缺失 / 类型不对（`band`、`id`、`title`；坐标写了就必须是数字）；`id` 重复；`band` 引用不存在；`edge.from/to` 指向不存在的节点；自环；`sSide`/`tSide` 非法；`sRatio`/`tRatio` 越界；`arrow`/`dashed`/`parallel` 非布尔；**同一对节点两条边**（除非双方 `parallel: true`）。

**警告（仍 PASS，通常该修）**：节点缺 `sub`、边缺 `url`、层缺 `color`、节点越界、节点重叠（有时是有意的叠层）。

### 2) 几何质量校验

```bash
node <技能目录>/scripts/quality.mjs <文件.pano>
```

显式写入 `points` 时，质量门要求每一段水平或垂直，且不能穿过其它节点；
显式坐标下会检查节点间距。自动布局的交叉、标签避让和最终视觉效果必须在 IDE 中打开 `.pano` 人眼确认。

### 3) 渲染自检（改了链路 / 动画时必跑）

在插件页面里执行与本技能同目录的 `scripts/hover-check.js`：

```js
await panoHoverCheck()   // => { pass: true, failures: [], rows: [...] }
```

逐节点断言：流动点存在且在动、无接缝跳变、高亮成链且有压暗对比、悬停卡片内容够（分段、角色、意图）。
失败信息会指出是哪个节点、哪条链路断了——通常是**数据缺边**，不是动画坏了。

### 4) 人眼确认

- 管线只走横竖（斜线 → 多半写死了 `sSide`，删掉让它重算）；
- 标注不压线、不互相重叠；同层对齐、层间留白、颜色可区分；
- 闭环看得出「走出去又回来」；**逐条念一遍链路**，重点查「有没有断头路、有没有回程」。

失败时**改规则，不改文案**：

| 现象 | 修法 |
| --- | --- |
| 解释只有标题副标题 | 检查推导是否真的执行（数据是否给了 `sub` / 边标签） |
| 角色明显不对 | 补 6.2 的语义类别，而不是特判某节点 |
| 在链路中的位置只列节点名 | 链路从「无入边的入口节点」开始推导 |
| 链路碎 | 用 6.5 生成链路并集 |
| 点看着不动 | 速度随长度自适应，别写死 |

## 十二、失败后的修正路径

| 现象 | 先判断哪一层 | 修正动作 |
| --- | --- | --- |
| 节点或连线事实不对 | 事实层 | 回到代码/文档/部署素材，删除无依据关系 |
| hover 只能复述名字 | 语义层 | 补 `sub`、边 `url` 和条件，不增加图外说明 |
| 节点文字溢出 | 布局层 | 删除压缩坐标，或提高节点最小尺寸与间距 |
| 连线交叉/穿节点 | 布局层 | 让插件重新布线；必要时只调整节点相对位置 |
| 标签遮住节点/连线 | 布局层 | 增加节点间距或调整标签位置，不改动作文案 |
| 图能看但 hover 不联动 | 渲染层 | 检查边方向、入口、链路闭环和 hover 质量门 |

不要同时改四层；每次只修一个层级，再重新运行两个校验。

## 十三、常见错误与反例

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 打开一片空白 | YAML 语法错（缩进、tab、中文冒号） | 用 `check.mjs` 复现并改语法 |
| 节点没颜色 / 图例少一项 | `node.band` 引用了不存在的层 | 补 `bands` 或改 `band` |
| 连线指向空气 | `edge.from/to` 拼错，或节点 id 改过没同步 | 同步 id |
| 线斜着走 | 手写了 `sSide` 后节点又挪了位置 | 删掉接入侧让渲染器重算 |
| 出现两条重合的线 | 为双工连接画了两条边 | 只留一条 |
| 悬停卡片内容很空 | 缺 `sub`、边缺 `url`、层 `label` 太泛 | 补形态与动作 |
| 越改越乱、坐标全乱 | 丢掉了界面里的手工微调 | 先读全文，只改必要字段 |
| 图看不懂层次 | 层按团队 / 仓库切了，或层太多 | 按运行位置重切，3–6 层 |
| 双击打开的是文本 | 插件注册缺失（`customEditors` 与关联都要有） | 见项目侧插件配置 |
| 改了打开方式报 `INVALID tab` | OpenSumi 宿主 tab 表缺 id | 打补丁并清 webpack 缓存后重启 |
| 插件里改了没保存 | 误以为要手动保存 | `.pano` 由插件自动写回，不需要手动保存 |

**反例（都被否过）**：树冠弧形布局；贝塞尔 S 曲线 / 抛物线；直角硬折线；连线从节点内部出发或贴着边框滑行；多条线接入同一点；为回程画第二条边；普通连线加箭头 / 实心三角箭头；层名写英文组件名或 `svc`/`deploy`；基础设施层放 ConfigMap/Secret；高亮横向扩散到整个连通图；照抄参考图的节点名（参考图只借样式，不借数据）。

## 十四、字段填写规则

- 所有值必须由当前需求推导，**不得沿用任何示例中的层名、节点名、颜色或坐标**；
- 连线形状与标签位置默认交给插件自动计算：**不要主动写 `points` / `label`**；只有用户明确要求，或自动结果明显不合理时才写（`points` 写入后不再自动布线）；
- 默认不写 `x` / `y` / `w` / `h`：让插件自动分层布局；只有需要精确摆放时才写，写了就整图不再自动排版；
- 字段合法性以 `scripts/check.mjs` 为准；新增字段只在插件已实现时写入，不写未落地的字段；
- 改的顺序：`bands` 定层与配色 → `nodes` 定实体与坐标 → `edges` 定动作 → 跑校验 → 请人看。

## 十五、与渲染层的边界（不写安装步骤）

- **`*.pano` / `*.panorama` 是唯一正式数据源**，YAML（兼容 JSON），由工作台插件在 IDE 里渲染；
- 插件负责：新增 / 拖节点 / 改大小 / 双击改标题 / 拖出连线 / 连线工具条（箭头、虚线、清形、标签复位、删除）/ 选中连线后拖折点改形状、拖标签改位置 / 缩放适应居中 / 全屏 /
  悬停解释卡片与链路流动动画 / **改动自动写回文档并由 IDE 保存**；
- `.pano` 是唯一数据源，也是唯一交付物；
- **不要生成任何预览文件**（HTML / SVG / PNG 等）：看效果一律在 IDE 里打开 `.pano`；
- 人要装插件、要打开文件属于使用侧文档，不在本技能范围；本技能只对**数据内容**负责。

> 交付时给出：文件路径 + 这张图讲什么 + 哪些地方是简化过的 + 校验结果（PASS 行）。

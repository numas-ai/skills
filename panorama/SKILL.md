# 维护一张全景图（`*.pano` 数据文档）

**这个技能管的是 `.pano` 的内容**：什么时候该画、内容怎么从素材推导、字段怎么写、改完怎么校验。
**渲染与交互由插件 `numas.panorama` 负责**（它不是本技能的主题，只在第十节说明边界）：
插件把数据画成图、支持拖拽编辑、悬停解释、流动动画；人看图给反馈，AI 改数据。

一句话分工：**AI 维护数据，插件负责让人看懂，人负责判断对不对。**

```
人：要一张能看懂 X 的全景图 / 这里改一下
AI：改 .pano（本技能）→ 跑校验 → 交付
人：在插件里看效果、拖两下微调 → 继续提要求
```

## 一、什么时候该产出 `.pano`

命中下面任意一条就该画：

- 要讲**系统由哪些部分组成、彼此怎么连**（分层 + 调用关系），而不是单条请求的先后；
- 要讲**闭环**：流量走出去又回来、控制面与数据面如何配合（隧道、回连、注册激活这类）；
- 要让人**一张图看懂全貌**，并能按需深入某个节点（悬停看它是什么、为什么存在）；
- 已有 `.pano` 所描述的系统**发生了变化**（新增服务、换了入口、改了链路），需要同步更新。

**不该用 `.pano` 的场景**（选了会做无用功）：

| 需求 | 更合适的产物 |
| --- | --- |
| 一次请求/一次调用的先后顺序 | 时序图 |
| 精确数值、对比 | 表格 |
| 文件/类/模块的从属目录 | 目录树或依赖图 |
| 只有两三个节点的简单关系 | 一段文字或一句说明 |

## 二、内容怎么从素材推导出来

顺序固定：**先边界 → 再分层 → 再节点 → 再连线 → 最后语义标签与布局**。
跳步最典型的后果是「节点一堆、看不出层次」，或「连线都在、说不清发生了什么」。

### 1) 先定边界

明确这张图回答什么问题、到哪一层为止（要不要画到 Pod 级别？要不要画用户侧？）。
边界写进交付说明，不要靠读者猜。

### 2) 分层（`bands`）

层的划分依据是**运行位置与职责**，不是团队/代码仓库。常见切法：

| 层 | 判据 | 典型成员 |
| --- | --- | --- |
| 本地 / 用户侧 | 跑在用户机器上、不在平台内 | 桌面端、本地沙箱、本地代理 |
| 入口层 | 外部流量唯一的收口点 | 反代、ingress、网关入口 |
| 应用层 | 平台里做业务决策、创建资源的服务 | 控制面服务、调度服务 |
| 基础设施层 | 提供网络、调度、存储的底座 | 集群 API、覆盖网控制器、数据库 |

规则：

- 一个节点只属于一层（`node.band` 只能一个值）；
- 层数控制在 3–6 个，多了图例变噪音、颜色也分不清；
- 颜色用 `#rrggbb` 且互相能区分（浅底深底都要看得见）；
- **不要为「团队」「代码仓」建层**——那和图要讲的运行关系无关。

### 3) 节点（`nodes`）

节点是**有独立职责、可被单独访问 / 调度 / 替换的单元**，不是「每个组件都来一个」。

判定问句：*「它会不会单独出现在某条调用链上、单独挂掉会被单独引用？」*
是 → 建节点；否 → 收进 `sub` 里一句话交代。

必写两段文字，渲染层的解释全靠它们（见第五节）：

- `title`：**它是谁**（服务名 / 组件名，不要写句子）；
- `sub`：**它是什么形态、靠什么工作**（技术栈或形态关键词，如 `opensumi/node + opencode/sdk`、`Controller + Edge Router`、`前端 · 与后端分离`）。

粒度参考：一张 10–20 个节点的图最容易读懂；超过 25 个先问「能不能拆成两张」。

### 4) 连线（`edges`）

一条边 = **一次真实发生的连接**，方向按**发起方 → 承接方**写。

- **双工连接只画一条边**（隧道、长连接、双向流）。回程用动画表达，不要补一条 `B → A`；校验脚本会直接拦。
- 只有**条件分支**才 `arrow: true`；可选 / 非主链路用 `dashed: true`；两者都不是就别标。
- 手写 `sSide` / `tSide` 只在必须固定走线时用；一旦节点挪位就会变斜线，**默认交给编辑器自动选最近边**。
- 同一对节点不要出现两条平行边（除非确实两条独立通道，且双方都标 `parallel: true`）。

### 5) 语义标签（`edge.url`）

`url` 字段名是历史遗留，**内容是连线标注，写「发生了什么动作」**：

| 差 | 好 | 为什么 |
| --- | --- | --- |
| 空 | `已存在 → 路由` | 空白标签让读者无法判断这是路由、调用还是调度 |
| `ide.example.com` | `本地访问 · localhost:24096` | 只有 host 时读者不知道这条线做什么 |
| `注册` | `注册·激活（出站）` | 补上方向与阶段，才看得出握手顺序 |

判断标准：**只看这条线两端和标签，别人能不能说出「发生了什么」**。不能就补动作。
地址仍要写就写进标签里（`网关入口 · sandbox-gateway.example.com`），不要只留地址。

## 三、文件格式

```yaml
title: ''            # 目前只存不显示
subtitle: ''
canvas: { w: 1600, h: 900 }   # 画布逻辑尺寸，决定「适应 / 居中」
nodeHeight: 72                # 新节点默认高度
bands:                        # 层：图例文字 + 颜色
  - { id: app, label: webapp, color: '#58a6ff' }
nodes:
  - id: web                 # 唯一，被 edge 引用
    band: app               # 必须是已定义的 band.id
    title: webapp           # 它是什么
    sub: 前端 · 浏览器       # 什么形态、靠什么工作
    x: 480                  # 左上角坐标与宽高（px）
    'y': 60                 # YAML 里 y 会被加引号，两种写法都能读
    w: 240
    h: 72
edges:
  - from: web
    to: ingress
    url: 本地访问 · localhost:24096
```

| 层级 | 字段 | 必要性 | 说明 |
| --- | --- | --- | --- |
| 根 | `canvas.w` / `canvas.h` | 必填 | 画布逻辑尺寸（正整数） |
| 根 | `nodeHeight` | 可选 | 新节点默认高，缺省 72 |
| 根 | `title` / `subtitle` | 可选 | 目前只存不显示，可留空 |
| band | `id` / `label` / `color` | 必填 | 颜色必须 `#rrggbb` |
| node | `id` / `band` / `title` / `x` / `y` / `w` / `h` | 必填 | `band` 必须是已定义的层；`w`/`h` 为正 |
| node | `sub` | 强烈建议 | 缺了校验只给警告，但解释会退化成「只有名字」 |
| edge | `from` / `to` | 必填 | 两端必须是节点 id |
| edge | `url` | 强烈建议 | 缺了校验只给警告，但这条线的语义就丢了 |
| edge | `sSide` / `tSide` | 可选 | `top` `right` `bottom` `left`；不写由编辑器自动选最近边 |
| edge | `sRatio` / `tRatio` | 可选 | 接入点在边上的位置，0–1 |
| edge | `arrow` / `dashed` | 可选 | 布尔；箭头只给条件分支 |
| edge | `parallel` | 可选 | 布尔，**校验用标记**：同一对节点确需两条独立通道时成对标注，渲染层不读 |

## 四、从零生成：可执行步骤

1. **读素材**：把要表达的系统的组件、调用、部署位置读全（代码、文档、部署清单）。
2. **定边界与层**：写出这张图回答的问题 + 3–6 个层。
3. **列节点**：按第二节的粒度判据筛一遍，给每个节点写 `title` + `sub`。
4. **列连线**：写成「A --动作--> B」的清单，双工合并成一条，确认每条的发起方。
5. **排坐标**（规则见下），先落成草稿 `.pano`。
6. **跑校验**：`node skills/panorama/scripts/check.mjs <file.pano>`，修到 `PASS`。
7. **交付**：文件路径 + 这张图讲什么 + 已知取舍；请人在插件里看效果，按反馈再改。

坐标布局规则（让后续微调省事）：

- **层是横向的**：同一层节点 `y` 对齐；
- 上层到下层 ≥ 120px 垂直间距；同层相邻节点 ≥ 40px 水平间距；
- 宽节点（网关、入口这类）跨列时居中于它服务的下游，别贴边；
- 画布比内容多留 10%–15% 边距，避免「适应」后贴边；
- 坐标不必一次到位：先摆出层次，剩下的交给人在界面里拖（拖完会自动写回文件）。

## 五、数据必须能「自己解释」

插件不讲稿子，它**从结构推导**每个节点的说明并做成悬停卡片。
所以字段不是装饰，缺一项就少一段解释：

| 卡片内容 | 从哪来 | 缺了会怎样 |
| --- | --- | --- |
| 名字 / 副标题 | `title` / `sub` | 认不出它是谁 |
| 所属层 + 颜色 | `node.band` → `band.label` | 结构校验直接报错（讲不出它在哪一层） |
| 角色（入口 / 中间环节 / 终点 / 汇聚 / 分发） | **连线的方向与数量** | 图里的边不够，角色就说不准 |
| 意图（为什么存在） | **`band.label` 与 `sub` 里的关键词** | 只剩一句泛泛的「承担该层职责」 |
| 上下游是谁、怎么连 | 边的两个端点 + `edge.url` | 只能报节点名，说不出调用方式 |
| 在模式中的位置 | 入口节点出发的链路 | 没有明确入口节点时这一栏不出现 |

渲染层识别这些关键词（写数据时可据此对齐措辞，不是强制）：

| 关键词落在哪 | 触发的推导 |
| --- | --- |
| 边标签含 `隧道` / `bind` / `dial` / `回环` | 视为隧道类连接，参与「双工 / 隧道发起 / 汇聚点」判定 |
| 边标签含 `注册` / `激活` / `enroll` / `确认` | 视为控制面动作，用于「先握手再建隧道」这类角色 |
| `band.label` 含 `入口` / `接入` / `应用` / `基础设施` / `本地` | 决定层的职责描述 |
| `sub` 含 `前端` / `Controller` / `Router` / `ingress` / `按 host` / `API Server` / `沙箱创建` 等 | 决定形态意图 |

> 事实说明：插件内置了一张按节点 id 写死的「模式链路表」，只有与它同源的数据才会额外出现「在模式中的位置」一栏；
> 其它数据的角色 / 意图 / 上下游仍由结构推导。给别的项目画图时，不要依赖那一栏。

## 六、更新已有 `.pano`

改一张已有的图，风险不在「画得对不对」，而在**把别人的手工微调弄丢**。

1. **先读全文**，不要凭记忆重建（文件里可能已有在界面里拖出来的坐标）；
2. **只改该改的**：新增/删除节点或边时，不动无关节点的 `x/y/w/h`；
3. **`id` 保持稳定**：改 id 必须同步所有 `from`/`to`，否则连线指向空气；
4. **删除节点时一并删掉它的边**，别留悬空引用；
5. **新增一层时补齐所有节点的 `band`**，不要留空；
6. 改完立刻跑校验，再交付。

> 文件是 YAML（JSON 也能读，保存后变 YAML）。编辑器改动 **600ms 自动写回**，
> 所以人工微调不需要「保存」；AI 改文件时也别同时让人在界面里拖同一份文件。

## 七、交付前质量门

按顺序过，前三项可复现，最后一项必须人看。

### 1) 结构校验（数据层）

```bash
node skills/panorama/scripts/check.mjs <文件.pano>
```

`PASS` = 能被插件正常渲染且具备最小语义；`FAIL` 退出码非 0。判定分两档：

**错误（FAIL，必须修）**

- 字段缺失 / 类型不对：`canvas.w/h`、`band.id/label/color`、`node.id`、`node.band`、`node.title`、`node.x/y/w/h`；
- `id` 重复、`band` 引用不存在的层、`edge.from/to` 指向不存在的节点、自环；
- `sSide`/`tSide` 非法、`sRatio`/`tRatio` 越界、`arrow`/`dashed` 非布尔；
- **同一对节点两条边**（除非两条都标了 `parallel: true`）。

**警告（仍 PASS，但通常该修）**

- 节点缺 `sub`、边缺 `url`、层缺 `color` —— 图能打开，但解释与配色会退化；
- 节点越出画布、节点互相重叠 —— 有时是有意（如叠层），否则把坐标挪开。

### 2) 渲染自检（可选，改动了动画/链路语义时跑）

在 IDE 里用插件打开 `.pano` → 开发者工具控制台粘贴 [`scripts/hover-check.js`](scripts/hover-check.js)：

```js
await panoHoverCheck()   // => { pass: true, failures: [], rows: [...] }
```

逐节点断言：流动点存在且在动、无接缝跳变、高亮成链且有压暗对比、悬停卡片内容够（分段、角色、意图）。
失败信息会指出是哪个节点、哪条链路断了——通常是**数据缺边**，不是动画坏了。

### 3) 人眼确认

- 管线只走横竖（出现斜线 → `sSide` 写死了，删掉让它重算）；
- 标注不压在线上、不互相重叠；
- 同层对齐、层间留白，颜色能区分；
- 闭环看得出来「走出去又回来」（缺边补边）。

## 八、常见错误

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 打开一片空白 | YAML 语法错（缩进、tab、中文冒号） | 用 `check.mjs` 复现，改语法 |
| 节点没颜色 / 图例少一项 | `node.band` 引用了不存在的层 | 补 `bands` 或改 `band` |
| 连线指向空气 | `edge.from/to` 拼错，或节点 id 改过没同步 | 同步 id |
| 线斜着走 | 手写了 `sSide` 后节点又挪了位置 | 删掉 `sSide` 让编辑器重算 |
| 图上出现两条重合的线 | 为双工连接画了两条边 | 只留一条 |
| 悬停卡片内容很空 | 缺 `sub`、边缺 `url`、层 `label` 太泛 | 补形态与动作，见第五节 |
| 越改越乱、坐标全乱 | 丢掉了界面里的手工微调 | 先读全文，只改必要的字段 |
| 图看不懂层次 | 层按团队/仓库切了，或层太多 | 按运行位置重切，3–6 层 |

```yaml
title: ''

canvas: { w: 1200, h: 700 }
nodeHeight: 72
bands:
  - { id: local, label: 本地服务,       color: '#c084fc' }
  - { id: edge,  label: 接入层服务,     color: '#fbbf24' }
  - { id: svc,   label: 应用层服务,     color: '#f472b6' }
  - { id: infra, label: 基础设施层服务, color: '#34d27b' }
nodes:
  - { id: client,  band: local, title: 本地客户端,   sub: 桌面端 · 直连平台, x: 120, 'y': 60,  w: 200, h: 72 }
  - { id: ingress, band: edge,  title: nginx-ingress, sub: 统一入口 · 按 host 分发, x: 120, 'y': 220, w: 760, h: 72 }
  - { id: api,     band: svc,   title: api-server,   sub: opensumi/node · 业务编排, x: 200, 'y': 400, w: 220, h: 72 }
  - { id: db,      band: infra, title: postgres,     sub: 主库 · 持久化, x: 200, 'y': 560, w: 220, h: 72 }
edges:
  - { from: client,  to: ingress, url: 本地访问 · localhost:24096 }
  - { from: ingress, to: api,     url: 已存在 → 路由 }
  - { from: api,     to: db,      url: 读写 }
```

改的顺序：`bands` 定层与配色 → `nodes` 定实体与坐标 → `edges` 定动作 → 跑校验 → 请人看。

## 十、与渲染层的边界（不写安装步骤）

- **`*.pano` / `*.panorama` 是唯一数据源**，YAML（兼容 JSON），由插件在 IDE 里渲染；
- 插件负责：拖节点 / 改大小 / 双击改标题 / 拖出连线 / 连线工具条（箭头、虚线、删除）/ 缩放适应居中 / 全屏 /
  悬停解释卡片与链路流动动画 / **600ms 自动写回文件**；
- 静态预览 `index.html` 只做高亮：没有流动动画、没有解释卡片，**不适合当交付物**；
- 人要装插件、要打开文件属于使用侧文档，不在本技能范围；本技能只对**数据内容**负责。

> 交付时给出：文件路径 + 这张图讲什么 + 哪些地方是简化过的 + 校验结果（PASS 行）。
